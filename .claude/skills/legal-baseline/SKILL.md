# legal-baseline

두 검토자가 같은 잣대로 보려면 잣대가 먼저 있어야 한다. 기준 문서가 그 잣대다. 기준은 원문에서 오고, 확인한 날짜가 붙고, 무엇을 보면 지킨 것인지 판정할 수 있어야 한다. 그리고 어떤 규범이 걸리는지는 서비스의 사실이 가른다.

| 문서 | 경로 | 누가 읽나 |
| --- | --- | --- |
| 법무 기준 | `docs/live/legal-review/legal-baseline.md` | `riot-policy-reviewer`, `legal-reviewer`, 계획을 쓰는 `planner`, 고치는 팀 |

이 Task가 고칠 수 있는 것은 이 문서와 `_workspace/legal-review/`뿐이다. 이 문서는 참고용 검토의 기준이다. 법률 자문이 아니다.

## 원칙

| 원칙 | 이유 |
| --- | --- |
| 서비스의 사실을 먼저 적는다. 정해지지 않은 사실은 지어내지 않는다 | 수익이 있는가, API를 쓰는가, 누가 운영하는가에 따라 걸리는 조항이 달라진다 |
| 규범마다 출처의 주소, 문서에 적힌 개정일(법은 시행일), 확인한 날짜를 적는다 | 정책과 법은 바뀐다. 날짜 없는 기준은 믿을 수 없다 |
| 조항은 원문 그대로 옮긴다. 확인하지 못한 문장은 "원문 미확인"으로 표시한다 | 풀어 쓴 문장은 뜻이 달라진다 |
| 걸리는지 분명하지 않은 규범은 "조건부"로 넣고 조건을 적는다 | 놓친 위험이 지나친 점검보다 비싸다 |
| 조항마다 판정 기준을 붙인다. "무엇을 보면 지켰다고 하는가" | 판정할 수 없는 줄은 검토자마다 다르게 읽는다 |
| 규범이 답하지 않는 것은 답을 지어내지 않고 미결로 둔다 | 해석은 사용자와 전문가의 몫이다 |
| 법과 정책은 다른 축이다. 법은 법률, 시행령, 고시의 위아래가 있고, 권리자의 정책은 따로 선다 | 정책이 허락해도 법이 막을 수 있고, 그 반대도 있다 |
| 같은 수치와 문장은 이 문서에만 둔다 | 스킬의 출발 점검표와 어긋나면 이 문서가 정본이다 |

## 절차

1. **서비스의 사실.** 브리프의 `## 사용자 결정`, 설계서, 아키텍처 문서, 자산 연동 규약, 코드의 실제 구조에서 아래를 모은다. 정해지지 않은 것은 `## 결정 필요`에 올린다.

   | 사실 | 왜 필요한가 |
   | --- | --- |
   | 공개 범위와 운영 주체(개인인지 법인인지) | 권리자 정책의 허락 범위, 법의 적용 대상 |
   | 수익(광고, 후원, 결제, 유료 재화) | 비상업 조건, 표시 의무, 거래 관련 법 |
   | 권리자의 것(캐릭터, 이름, 로고, 음악, 영상)과 그 쓰임 | 정책의 조항, 저작권과 상표 |
   | 대회, 팀, 선수에 관한 콘텐츠 | 제3자의 권리, 초상과 이름 |
   | Riot API와 그 밖의 외부 서비스 | 개발자 정책, 각 서비스의 약관, 정보의 국외 이전 |
   | 계정과 모으는 정보, 이용자의 나이 | 개인정보, 아동, 청소년 보호 |
   | 이용자끼리의 대화와 이용자가 올리는 것 | 신고와 삭제, 불법 정보 |
   | 배포(웹인지 앱 장터인지)와 게임으로 볼 요소 | 정책의 게임·앱 조항, 게임물 해당 여부 |

2. **적용되는 규범.** 사실에 걸리는 정책과 법을 "필수"와 "조건부"로 나눠 표로 만든다. 출발점은 `riot-policy-review`의 `references/policy-map.md`와 `law-review`의 참조 문서다. 출발점을 그대로 옮기지 않는다. 원문을 열어 개정일과 문장을 확인하고 옮긴다. 열지 못한 것은 "원문 미확인"으로 적고 `## 결정 필요`에 올린다.
3. **조항과 판정 기준.** 조항을 의무 한 줄씩으로 쪼갠다. 줄마다 기준 ID(`RIOT-01`, `LAW-01`), 종류(허락, 금지, 표시, 동의, 기록), 원문, 서비스에서 걸리는 지점, 판정 기준, 담당 검토자를 적는다.
4. **반드시 표시할 문구.** 고지문처럼 문장 자체가 요구되는 것은 원문 그대로 적고, 근거와 표시할 자리의 요건을 적는다.
5. **미결.** 규범이 뜻을 정하지 않았거나 문서끼리 어긋나는 것을 적는다. 정해질 때까지의 처리는 조심스러운 쪽으로 적고, 누가 정하는지(사용자, 전문가) 적는다.
6. **다시 확인할 때.** 규범마다 다시 확인할 조건을 적는다: 정책 페이지의 개정일이 바뀜, 법의 개정이 시행됨, 수익·로그인·결제·외부 API가 더해짐, 새 종류의 콘텐츠를 다룸, 대회 기간의 시작.
7. **심각도의 기준.** 두 검토자가 같은 기준으로 등급을 매기도록 이 문서에 한 번 적는다. 출발값은 아래다.

   | 심각도 | 기준 |
   | --- | --- |
   | High | 원문 조항과 직접 어긋난다. 반드시 표시하거나 받아야 하는 것(고지문, 동의)이 빠졌다. 출처와 이용 조건을 댈 수 없는 것을 공개해 쓴다. 공식으로 오인될 표시다 |
   | Medium | 조건이 바뀌면 어긋난다. 일부만 지켰다. 근거 조항의 문장을 확인하지 못했다 |
   | Low | 어긋나지 않으나 더 분명히 할 수 있다 |
   | 등급 없음 | 해석이 갈리거나 규범이 답하지 않는다. `판단 필요`로 사람에게 넘긴다 |

현재 상태만 담는다. 대체된 조항과 지난 경과는 지운다. 확인한 날짜는 경과가 아니라 현재 상태다.

## 기준 문서의 뼈대

```markdown
# 법무 기준

- 읽는 시점: 정책이나 법에 닿는 기획을 할 때, 법무 검토를 할 때, 검토 Task의 spec을 쓸 때
- 역할과 소유 범위: 이 서비스에 적용되는 정책과 법, 판정 기준. 참고용 검토의 기준이며 법률 자문이 아니다
- 소유 에이전트: legal-leader
- 마지막으로 갱신한 phase: <phase>

## 1. 서비스의 사실
| 사실 | 값 | 출처(사용자 결정, 설계서, 코드) | 확정 / 가정 |

## 2. 적용되는 규범
| 규범 | 필수 / 조건부(조건) | 출처 주소 | 개정일이나 시행일 | 확인일 | 걸리는 이유 |

## 3. 조항과 판정 기준
| 기준 ID | 종류 | 원문(문서, 위치) | 서비스에서 걸리는 지점 | 판정 기준 | 담당 |

## 4. 반드시 표시할 문구
| 문구(원문 그대로) | 근거 | 표시할 자리의 요건 |

## 5. 미결
| 쟁점 | 왜 갈리는가 | 정해질 때까지의 처리 | 누가 정하나 |

## 6. 심각도의 기준

## 7. 다시 확인할 때
| 규범 | 다시 확인할 조건 | 마지막 확인일 |

## 결정 필요
| 정할 것 | 후보 | 추천 | 사용자 결정인가, 전문가 확인인가 |
```

## 하지 않는 것

- 약관, 처리방침, 고지문을 쓰지 않는다. 무엇이 들어가야 하는지의 요건만 적는다.
- 법적 결론을 내리지 않는다. "된다", "안 된다"가 아니라 조항과 판정 기준을 적는다.
- 권리자나 기관에 문의하거나 신청하지 않는다. 필요하면 `## 결정 필요`에 올린다.
- 제품의 코드, 자산, 문구를 고치지 않는다.

## 완료 기준에 쓸 수 있는 검사

- 1절의 사실마다 출처와 확정인지 가정인지가 있다. 가정인 줄은 `## 결정 필요`에 대응하는 줄이 있다.
- 2절의 규범마다 출처 주소, 개정일이나 시행일, 확인일이 있다. 없는 줄은 "원문 미확인"으로 표시돼 있다.
- 3절의 줄마다 판정 기준과 담당이 있다.
- 4절의 문구가 원문과 한 글자도 다르지 않다(원문 주소를 열어 대조).
- 5절의 줄마다 정해질 때까지의 처리와 누가 정하는지가 있다.
- 문서에 날짜 붙은 경과와 대체된 조항이 없다.
