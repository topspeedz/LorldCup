# team-legal-review

법무검토팀은 서비스가 지켜야 할 것을 한곳에 모으고, 지켰는지를 근거와 함께 본다. 고치지 않는다. 결론을 내리지도 않는다. 이 팀의 산출물은 참고용 검토이며 법률 자문이 아니다. 해석이 갈리는 것은 사람에게 넘긴다. 팀장은 spec 첫 줄이 `[역할: legal-leader · 리드]`인 워커이며 `team-lead`와 이 스킬을 로드한다.

## 에이전트 구성

| 에이전트 | 맡는 일 | 역할 스킬 | 모델 표의 작업 단위 |
| --- | --- | --- | --- |
| `legal-leader` | 기준 문서 쓰기: 서비스의 사실, 적용되는 정책과 법, 판정 기준, 미결 | `legal-baseline` | 법무 기준 |
| `riot-policy-reviewer` | Riot의 공개 정책 원문과 서비스의 대조. 리포트만 쓴다 | `riot-policy-review` | Riot 정책 검토 |
| `legal-reviewer` | 지식재산과 서비스 운영 관련 법의 검토. 리포트만 쓴다 | `law-review` | 법률 검토 |

- 작업 단위는 모델 표에 있는 이름만 쓴다. 없으면 표에 줄을 먼저 넣는다.
- 팀장으로 뜬 `legal-leader`는 기준 문서를 직접 쓰지 않는다. 같은 에이전트를 일반 Task로 따로 띄운다.

## 배치

- **기준이 먼저다.** 기준 문서가 없거나, 서비스의 사실이 바뀌는 phase(수익, 로그인, 채팅, 결제, 외부 서비스, 새 종류의 콘텐츠)에는 01을 먼저 돌린다.
- **앞 검토는 만들기 전에 한다.** 이번 phase의 기획(브리프, 설계서)과 쓰려는 자산, 데이터, 수익 방식을 본다. 여기서 걸린 것은 만들기 전에 바꾼다. 구현 Task는 앞 검토에 의존으로 건다.
- **끝 검토는 공개하기 전에 한다.** 실제 코드의 문구와 고지, 자산의 출처 표, 모으는 정보, 서비스 문서를 본다. 그 영역의 구현 Task가 끝난 뒤에 돈다.
- **두 검토자는 함께 돈다.** 보는 근거가 다르다(권리자의 정책과 법). 같은 사실 표에서 출발하므로 01이 끝나면 동시에 띄운다.
- **읽어서 찾는다.** 서버와 브라우저를 띄우지 않는다. 화면에 실제로 보이는지처럼 실행해야 확인되는 것은 리포트의 `## 관찰`에 적어 검증 팀에 넘긴다.
- **원문은 검토 때마다 다시 연다.** 정책의 개정일이 기준 문서와 달라졌으면 검토자가 리포트 맨 위에 적고, 팀장은 01을 새로 띄운다.

## 작업 흐름

| 순서 | 작업 | 담당 | 의존 | 산출물 파일 |
| --- | --- | --- | --- | --- |
| 01 | 법무 기준: 기준 문서를 쓰거나 이번 범위에 맞게 고친다 | `legal-leader` | 브리프의 사용자 결정, 설계서 | `01_legal-leader_baseline_v1.md` |
| 02 | Riot 정책 검토: 앞 검토나 끝 검토 | `riot-policy-reviewer` | 01. 끝 검토면 대상의 구현 Task | `02_riot-policy-reviewer_review-<앞 또는 끝>_v1.md` |
| 03 | 법률 검토: 앞 검토나 끝 검토 | `legal-reviewer` | 01. 끝 검토면 대상의 구현 Task. 권리자의 것을 쓰는 문제를 볼 때는 02 | `03_legal-reviewer_review-<앞 또는 끝>_v1.md` |
| 04 | 재검: 고친 발견 ID만 다시 본다 | 원래 찾은 에이전트 | 그 루프의 수정 Task 전부 | 02나 03의 다음 버전 `_v<N+1>` |

- 순서 `NN`은 산출물 파일 이름의 `NN`이다. 도착 순서가 아니다.
- 판정: 두 리포트 모두 High가 0이면 승인이다. 고치는 것은 High뿐이고, Medium 이하는 인박스로 보낸다. `판단 필요`는 판정과 따로 사람에게 올린다.
- 고치는 것은 그 영역의 팀이다. 문구와 화면은 웹 개발 팀, 자산과 출처 표는 그래픽 팀이다. 이 팀은 고치지 않는다.
- 수정 루프는 최대 2회다. 2회 뒤에도 High가 남으면 멈추고 통합 보고에 남은 High를 적는다.
- 팀원 spec에는 검토 대상(문서, 경로, 자산 목록)과 볼 영역을 적는다. "전체를 봐 달라"는 spec을 쓰지 않는다. 서비스 전반을 볼 때는 영역으로 나눠 Task를 여러 개 만든다.
- 결함 ID의 접두어는 `riot-policy-reviewer`가 `RP-`, `legal-reviewer`가 `LG-`다.

**통합 보고(팀장).** 두 리포트를 읽고 아래를 한다.

- 같은 사실을 두 검토자가 다르게 판정했으면 고르지 않는다. 조심스러운 쪽을 적고 어긋난 것 자체를 기록한다.
- 두 리포트의 `판단 필요`를 모아 한 표로 만든다. 줄마다 선택지와 추천 하나를 붙인다.
- 밖으로 나가는 행위가 필요한 것(권리자에게 문의, 등록, 전문가 확인)을 따로 모은다. 그 행위는 사용자가 한다.
- 첫머리에 "참고용 검토이며 법률 자문이 아니다" 한 줄을 둔다.

## 팀원 간 소통

- 기본은 팀장을 거친다. 팀원은 산출물 파일과 팀장의 `ask`/`reply`로 주고받는다.
- 아래 **직접 소통 짝 표**에 있는 짝만 서로 직접 메시지를 보낼 수 있다(`send --to dispatch:<상대 id>`). 팀장은 짝의 두 팀원을 띄운 뒤 서로의 Dispatch ID와 한도를 알려 준다.
- 받는 쪽은 알림(`You have N orchestration messages`)을 보면 `orca orchestration check`로 읽는다.
- 직접 주고받아 정한 내용은 보낸 쪽이 자기 리포트의 `## 직접 소통` 절에 적는다.

### 직접 소통 짝 표

| 짝 | 방향 | 용도 | 한도 |
| --- | --- | --- | --- |
| `riot-policy-reviewer` ↔ `legal-reviewer` | 양방향 | 같은 사실을 정책과 법으로 각각 어떻게 보는지 확인 | 사실 하나에 질문 1회, 넘으면 팀장에게 |

- **한도 칸은 비울 수 없다.** 짝을 더하면 한도를 함께 적는다.
- 짝끼리 판정을 맞추지 않는다. 서로의 근거를 확인할 뿐이고, 어긋나면 각자 자기 판정을 적는다. 맞추는 것은 사람의 일이다.

## 작업 규모별 모드

| 모드 | 언제 | 투입 |
| --- | --- | --- |
| 풀 | 서비스의 사실이 바뀌거나(수익, 로그인, 채팅, 외부 서비스) 새 종류의 콘텐츠를 다룬다. 공개 전의 전체 점검 | 01, 02, 03. Task가 3개 이상이므로 팀장을 띄운다 |
| 축소 | 기준 문서가 있고 한쪽만 걸린다(자산 몇 개의 이용 조건, 문구의 변경) | 걸리는 쪽의 검토 Task 하나나 둘. 코디네이터가 직접 띄운다 |
| 단일 | 고지문 한 줄의 확인, 자산 하나의 이용 조건, 재검 | 해당 에이전트 Task 하나 |

## 산출물

- 리포트 경로: `_workspace/legal-review/<phase>/NN_<에이전트>_<산출물>_v<N>.md`. 지시서는 `_workspace/legal-review/<phase>/spec/`.
- 이미 넘긴 리포트는 고쳐 쓰지 않는다. 다시 쓰면 다음 버전 `_v<N+1>`을 만든다. `final`, `fix1`, `-2` 같은 접미사를 쓰지 않는다.
- 이 팀이 최신으로 유지하는 문서(`docs/live/legal-review/`, 현재 상태만 담는다):

| 문서 | 소유 에이전트 | 갱신하는 때 |
| --- | --- | --- |
| `docs/live/legal-review/legal-baseline.md` | `legal-leader` | 01. 서비스의 사실이 바뀐 phase, 검토자가 정책이나 법의 개정을 알린 phase, 사용자가 미결을 정한 phase |

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 정책이나 법의 원문을 열지 못했다 | 그 항목은 "확인 못 함"이다. 통과로 적지 않는다. 통합 보고에 확인하지 못한 규범의 목록을 적는다 |
| 서비스의 사실(수익, 운영 주체, 모으는 정보)이 정해지지 않았다 | 걸릴 수 있는 규범을 조건부로 모두 보고, 어떤 가정 위의 판정인지 적는다. 사실의 결정은 코디네이터에게 `ask` |
| 검토자가 정책의 개정을 알렸다 | 01을 새로 띄워 기준 문서를 고친 뒤, 영향을 받는 검토를 다시 띄운다 |
| 두 리포트가 같은 사실을 다르게 판정했다 | 팀장이 고르지 않는다. 조심스러운 쪽과 어긋난 것을 통합 보고의 `## 코디네이터 결정 필요`에 올린다 |
| `판단 필요`가 공개를 막을 만큼 무겁다 | 막을지 말지는 사용자가 정한다. 선택지와 추천을 붙여 올린다 |
| 검토 대상이 너무 넓다 | 영역(권리자의 것, 남의 자산, 개인정보, 서비스 문서, 이용자의 콘텐츠)으로 나눠 Task를 여러 개 만든다 |
| 팀원 실패 | 원인을 새 spec에 적어 새로 띄워 1회 재시도. 그래도 실패하면 그 검토 없이 통합 보고에 누락을 적는다 |

## 테스트 시나리오

- 정상: "캐릭터와 대회 관련 공간을 공개하기 전에 점검" → 풀 모드 → 01에서 서비스의 사실(수익 없음, API 안 씀, 계정과 채팅 있음)과 걸리는 규범을 기준 문서에 적고, 정책이 정의하지 않는 쟁점을 미결에 올림 → 02와 03이 함께 돈다. 02에서 고지문이 원문과 한 단어 달라 `RP-H-1`, 03에서 출처가 빈 자산 둘이 `LG-H-1`과 `LG-H-2`, 처리방침에 없는 수집 항목이 `LG-H-3` → 통합 보고에 High 넷과 `판단 필요` 하나 → 웹 개발 팀과 그래픽 팀이 고침 → 04에서 그 ID만 다시 봄 → 승인. `판단 필요`는 사용자에게.
- 기존 파일 활용: 기준 문서가 있고 "새 소품 다섯 개의 이용 조건 확인" → 축소 모드 → 01과 02를 건너뛰고 03만, spec의 "먼저 읽을 것"에 그래픽 팀 리포트의 `## 자산 출처`와 기준 문서의 사실 표를 넣는다.
- 오류: 02가 정책 페이지를 열었더니 개정일이 기준 문서와 다르다 → 02가 리포트 맨 위에 적고 바뀐 조항의 항목을 "확인 못 함"이 아니라 새 문장으로 대조해 보고함 → 팀장이 01을 새로 띄워 기준 문서를 고치고, 03에 영향이 있는지 본 뒤 필요한 검토만 다시 띄운다.
