# 여러 사용자

> 읽는 시점: `web3d-runtime` 8단계. 다른 사용자의 캐릭터를 보이거나, 상호작용을 주고받는 Task.

통신 방식(무엇으로 잇는가), 서버, 메시지 형식, 갱신 빈도는 아키텍처 문서가 정한다. 정해지지 않은 것을 구현하면서 정하지 않는다. `ask`로 올린다. 이 문서는 클라이언트 쪽이 지킬 원칙이다.

## 1. 누가 진실인가

| 원칙 | 이유 |
| --- | --- |
| 서버가 정하고, 클라이언트는 의도(입력)만 보낸다 | 클라이언트가 위치를 정하면 속이기 쉽고, 서로의 화면이 영영 어긋난다 |
| 내 캐릭터는 입력 즉시 움직이고(예측), 서버의 결과와 비교해 차이가 문턱을 넘으면 고친다 | 응답을 기다리면 조작이 굼뜨다 |
| 고칠 때는 순간 이동이 아니라 짧게 당겨 맞춘다. 차이가 아주 크면 순간 이동한다 | 작은 차이마다 튀면 조작감이 망가진다 |
| 클라이언트의 시계를 믿지 않는다. 순서는 서버가 매긴 번호로 정한다 | 기기마다 시계가 다르다 |
| 지연 때문에 틀려 보이는 요청은 무시만 한다. 내쫓는 것은 있을 수 없는 입력일 때뿐이다 | 정직한 사용자가 쫓겨난다 |

## 2. 다른 사용자의 캐릭터

- 받은 상태를 시각과 함께 버퍼에 쌓고, **조금 과거의 시점**(약 100 ms 전)을 두 상태 사이에서 보간해 그린다. 지금 시점을 그리려 하면 다음 상태가 올 때까지 멈췄다가 튄다.
- 버퍼가 비면 짧게 이어 그리다(외삽) 멈춘다. 오래 이어 그리지 않는다.
- 위치만 보간하지 않는다. 방향과 애니메이션 상태도 함께 보간하거나 전환한다. 위치는 걷는데 클립이 서 있으면 미끄러져 보인다.
- 처음 들어왔을 때와 순간 이동했을 때는 보간하지 않고 바로 놓는다.

## 3. 무엇을 얼마나 자주 보내나

| 종류 | 성격 | 다루는 법 |
| --- | --- | --- |
| 존재(위치, 방향, 보는 곳) | 금방 낡는다 | 잃어도 되는 통로. 새 값이 옛 값을 덮는다. 초당 10~30번이면 대부분 충분하다 |
| 일어난 일(인사, 획득, 채팅) | 한 번도 잃으면 안 된다 | 순서가 있는 통로. 번호를 붙인다 |
| 꾸밈(이펙트, 효과음) | 잃어도 놀이는 계속된다 | 잃어도 되는 통로. 놀이를 막지 않는다 |

- 존재와 일어난 일을 한 통로에 섞지 않는다. 둘 다 망가진다.
- 바뀐 것만 보낸다. 움직이지 않는 캐릭터의 위치를 계속 보내지 않는다.
- 보는 사람에게서 먼 것은 덜 자주 보낸다.

## 4. 끊김은 정상이다

- 다시 잇기를 잇기보다 먼저 설계한다. 마지막으로 확인한 번호부터 이어 받는다.
- 모든 요청에 클라이언트가 만든 식별자를 붙여, 같은 요청이 두 번 가도 한 번만 적용되게 한다.
- 다시 이은 뒤 내 캐릭터가 둘이 되지 않는지 확인한다.
- 탭이 숨었다 돌아오면 쌓인 것을 한꺼번에 재생하지 않고 지금 상태로 건너뛴다.

## 5. 둘이 함께하는 상호작용

하이파이브처럼 두 사용자가 한 순간을 맞추는 동작은 각자의 화면에서 시각이 다르다.

- 한쪽(서버나 시작한 쪽)이 시작 시각을 정하고, 양쪽이 그 시각에 맞춰 클립을 시작한다.
- 이펙트의 큐 표가 어느 쪽 시계를 기준으로 하는지 `spec.md`에 적혀 있다. 없으면 `ask`로 받는다.
- 늦게 도착하면 클립의 앞부분을 건너뛰고 맞닿는 순간에 맞춘다. 맞닿는 순간이 이미 지났으면 여운만 재생한다.

## 6. 시험

- 내 컴퓨터 안에서만 시험하지 않는다. 지연 100, 150, 200 ms와 일부 유실을 넣고 본다.
- 볼 것: 다른 캐릭터가 튀지 않는가, 클립이 위치와 맞는가, 끊었다 다시 이었을 때 중복이 없는가, 한 사람이 빠르게 반복해도 다른 사람의 화면이 따라오는가.
- 보간 버퍼, 순서 번호 처리, 중복 요청 걸러 내기는 렌더 없이 테스트한다. 가짜 시계와 가짜 통로로 늦게 오는 것, 순서가 바뀐 것, 두 번 오는 것을 넣는다.
