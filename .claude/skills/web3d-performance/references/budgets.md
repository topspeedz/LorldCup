# 예산과 점검표 (출발값)

> 읽는 시점: 성능 점검에서 기준값을 정할 때, 자산을 만드는 담당이 spec에 예산이 없을 때, 계획에서 자산 예산을 나눌 때.

**이 문서의 수치는 출발값이다.** 프로젝트의 정본은 자산 연동 규약 `docs/live/web-metaverse-develop/asset-contract.md`의 예산 절이다. 규약에 값이 생기면 그 값을 쓰고, 이 문서의 값은 쓰지 않는다. 출발값은 실측으로 고친다.

## 1. 한 프레임의 예산

화면에 보이는 한 프레임 기준이다.

| 항목 | 데스크톱 | 모바일 |
| --- | --- | --- |
| 프레임 시간 | 16.7 ms(초당 60장). 120 Hz 화면은 8.3 ms | 16.7~33 ms |
| 드로 콜 | 100~200 미만 | 50 미만 |
| 보이는 삼각형 | 100만 미만 | 10만 미만 |
| 텍스처 메모리 | 목표 약 150 MB, 상한 500 MB | 목표 약 50 MB, 상한 200 MB |
| 픽셀 비율 상한 | 1.75 (가로 2560 이상 2.0, 3840 이상 2.5) | 1.5 |
| 실시간 조명 / 그림자를 드리우는 조명 | 3~5 / 2~3 | 1~2 / 0~1 |
| CPU로 움직이는 파티클 | 수만 개(인스턴스) | 1,000 미만 |

초당 60장을 지키려면 약 2 ms의 여유가 있어야 한다. 16 ms가 걸리는 프레임은 자주 30장으로 떨어진다.

## 2. 자산 예산 나누기

메타버스는 한 화면에 여러 사용자가 보인다. 자산 한 개의 예산은 프레임 예산에서 나눠 구한다.

- 캐릭터 한 명의 삼각형 = (보이는 삼각형 예산 − 환경의 몫) ÷ 한 화면에 보이는 최대 캐릭터 수
- 캐릭터 한 명의 드로 콜 × 최대 캐릭터 수 + 환경의 드로 콜 + 이펙트의 드로 콜 < 드로 콜 예산
- 텍스처 메모리는 서로 다른 캐릭터와 환경의 텍스처를 모두 더한 값이 예산 안이어야 한다

한 화면의 최대 캐릭터 수는 설계가 정한다. 정해지지 않았으면 가정한 수를 리포트에 적는다.

**참고 예시.** 게임 엔진에서 흔히 쓰는 값이다. 웹과 모바일에서는 더 낮게 시작하고 실측으로 정한다. 모바일의 지오메트리는 데스크톱의 절반 안팎이 출발점이다.

| 자산 | 가까이 | 중간 | 멀리 | 아주 멀리 |
| --- | --- | --- | --- | --- |
| 캐릭터 (삼각형 / 텍스처) | 15,000 / 2048 | 8,000 / 1024 | 3,000 / 512 | 800 / 256 |
| 주요 소품 (삼각형 / 텍스처) | 4,000 / 1024 | 1,500 / 512 | 400 / 256 | – |

| 그 밖의 출발값 | 값 |
| --- | --- |
| 캐릭터의 드로 콜 | 2~3 |
| 캐릭터의 뼈 | 모바일 30~50개. 정점 하나에 영향을 주는 뼈 4개 |
| 삼각형 등급 | 6,000 이하는 가벼움, 60,000 이하는 보통, 그 위는 주인공 자산 |
| 자산 한 개의 내려받는 크기 | 약 5 MB 이하 |

## 3. 텍스처

- 그래픽 메모리 = 가로 × 세로 × 4바이트 × 1.33(밉맵). 4096은 약 89 MB다.
- 크기 상한: 일반 2048, 모바일 1024, 배경과 UI 512. 2의 거듭제곱. 정하지 않았으면 1024.
- KTX2(Basis)는 그래픽 메모리 안에서도 압축된 채로 있다(약 4~8배 작다). JPEG와 WebP는 내려받는 크기만 줄인다.
- KTX2로 바꿀 때 노멀과 금속·거칠기 맵은 UASTC, 색 맵은 ETC1S를 쓴다. 노멀에 ETC1S를 쓰지 않는다.
- 색 맵은 sRGB, 데이터 맵(노멀, 금속·거칠기·AO)은 선형. 데이터 맵에 JPEG를 쓰지 않는다.
- 금속·거칠기·AO는 한 장에 묶는다(R = AO, G = 거칠기, B = 금속). 읽는 횟수와 메모리가 준다.
- 비스듬히 보이는 바닥의 선명도(비등방 필터)는 4~8이면 충분하다.

## 4. 지오메트리와 드로 콜

- [ ] 같은 지오메트리와 재질이 약 50개를 넘으면 인스턴스로 그린다.
- [ ] 움직이지 않고 재질이 같은 것은 하나로 합친다. 텍스처가 여러 장이면 한 장에 모아 재질을 하나로 만든다.
- [ ] 같은 재질은 인스턴스 하나를 함께 쓴다. 값이 같은 재질을 따로 만들면 따로 묶인다.
- [ ] 쓰지 않는 UV 세트, 정점 색, 셰이프 키를 지운다.
- [ ] 가까이 보는 자산에는 거리별 단순 모델을 둔다.
- [ ] 바운딩 구가 맞아야 화면 밖의 것을 걸러 낸다. 위치를 고친 뒤에는 다시 계산한다.
- [ ] 압축을 고른다. Draco는 움직이지 않는 메시의 크기에 강하고 디코더가 필요하다. Meshopt는 애니메이션과 셰이프 키도 압축하고 푸는 속도가 빠르다. 양자화만 하면 디코더가 필요 없다. 어느 쪽이 더 작은지는 자료마다 말이 다르니 실제 파일로 잰다.

## 5. 재질, 조명, 후처리

- [ ] 재질의 비용: 조명 없는 것 < 단순 조명 < 표준 물리 기반 < 고급 물리 기반. 투과, 겉칠, 벨벳 광택은 주인공 자산에만 쓰고 모바일에서는 투과를 쓰지 않는다.
- [ ] 반투명은 비싸다. 오려 내기를 먼저 쓰고, 반투명은 깊이를 쓰지 않게 하고, 겹치는 층을 줄인다.
- [ ] 움직이지 않는 빛은 텍스처로 굽는다. 그림자 맵은 모바일 1024 이하. 움직이지 않는 그림자는 한 번만 그린다.
- [ ] 후처리의 비용: 색 보정 < 가장자리 어둡게 < 계단 지움 < 빛 번짐 < 주변 그늘 < 심도 흐림 < 화면 반사. 모바일은 심도 흐림과 주변 그늘을 빼고, 빛 번짐은 약하게, 절반 해상도로 한다.
- [ ] 계단 지움은 한 가지만 쓴다.

## 6. 이펙트

| 항목 | 모바일 | 데스크톱 |
| --- | --- | --- |
| 화면에 동시에 있는 파티클 | 500 | 2,000 |
| 효과 하나의 겹치는 반투명 층 | 3 이하 | 6 이하 |
| 파티클 텍스처 | 종류마다 256 이하, 한 장에 모은다 | |
| 이펙트의 드로 콜 | 10 미만 | |
| 파티클의 조명 | 픽셀마다 조명하지 않는다 | |

품질 단계(높음, 보통, 낮음)를 효과와 함께 만든다. 낮음에서는 텍스처 애니메이션을 끄고 먼 것은 그리지 않는다.

## 7. 증상에서 원인으로

| 증상이나 수치 | 원인 | 처방 |
| --- | --- | --- |
| 드로 콜이 많다 | 메시와 재질이 따로따로 | 인스턴스, 합치기, 한 장에 모으기, 재질 함께 쓰기 |
| 삼각형이 많다 | 멀리 있는 빽빽한 메시 | 거리별 단순 모델, 단순화, 화면 밖 걸러 내기 |
| 해상도를 절반으로 내리면 프레임이 크게 오른다 | 화면 채우기, 겹쳐 그리기, 무거운 픽셀 셰이더 | 픽셀 비율 상한, 싼 재질, 반투명 층 줄이기, 가벼운 후처리 |
| 물체가 처음 보일 때 멈칫한다 | 셰이더 컴파일이나 텍스처 올리기 | 보이기 전에 미리 컴파일하고 올리기, 작은 텍스처 |
| 메모리가 계속 는다 | 해제 누락이나 캐시 | 해제 절차, 로더 캐시 비우기 |
| 조명을 늘리면 전부 느려진다 | 픽셀마다 조명 수만큼 계산 | 굽기, 조명 줄이기, 환경 맵 |
| 캐릭터가 늘면 CPU가 찬다 | 뼈 계산, 애니메이션 갱신 | 뼈 줄이기, 화면 밖 캐릭터의 갱신 건너뛰기, 멀리 있는 것은 갱신 간격 늘리기 |
| 오래 돌리면 점점 느려진다 | 기기가 뜨거워져 스스로 속도를 낮춘다 | 평균 부하를 낮춘다. 실기기에서만 재현된다 |

## 8. 페이지 지표

3D가 있는 화면도 페이지의 지표를 따로 지킨다. 재는 것과 고치는 것은 `metaverse-web-developer`의 몫이고, 이 역할은 3D가 원인일 때 수치를 넘긴다.

| 지표 | 기준 |
| --- | --- |
| 가장 큰 내용이 그려지기까지(LCP) | 2.5초 이하 |
| 입력 뒤 다음 화면까지(INP) | 200 ms 이하 |
| 배치 밀림(CLS) | 0.1 이하 |
