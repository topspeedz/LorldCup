# web3d-performance

수치가 없는 지적은 하지 않는다. 먼저 재고, 하나만 바꾸고, 같은 조건에서 다시 잰다. 자산은 고치고 코드는 권고한다.

`qa-inspector`는 흐름이 **동작하는가**를 본다. 이 역할은 **얼마나 빠르고 무거운가**를 잰다. 결함 ID에는 접두어 `P-`를 붙인다(`P-H-1`).

## 원칙

| 원칙 | 이유 |
| --- | --- |
| 기준값(임계값)을 결과를 보기 전에 리포트 머리에 적는다 | 같은 입력에서 같은 후보가 나와야 한다 |
| 측정이 가리킨 곳만 판다. 나쁜 패턴 찾기부터 하지 않는다 | 사용자가 겪는 비용과 상관없는 긴 목록이 나온다 |
| 변경은 하나씩, 바꿀 때마다 다시 잰다 | 묶어서 바꾸면 무엇이 효과였는지, 무엇을 되돌릴지 모른다 |
| 세 번 넘게 재서 가운데 값을 쓰고 흩어진 정도를 적는다 | 잴 때마다의 차이가 대부분의 개선 폭보다 크다 |
| 평균이 아니라 가장 긴 프레임과 상위 구간(p95)을 본다 | 끊김은 평균에 묻힌다 |
| CPU 한계인지 GPU 한계인지 먼저 가른다 | 처방이 정반대다 |
| 재지 않은 효과를 약속하지 않는다 | 리포트 전체의 신뢰가 무너진다 |
| 이미 켜진 설정을 켜라고 하지 않는다. 설치된 버전에 없는 API를 권하지 않는다 | 같은 이유 |

## 성능 점검 절차

1. **범위와 예산.** spec에서 대상(자산 목록, 장면, 화면), 기기 등급(데스크톱, 모바일), 실행 방법을 받는다. 예산은 자산 연동 규약이 정본이고, 없으면 [references/budgets.md](references/budgets.md)의 출발값을 쓰고 "출발값 사용"이라고 적는다. 기준값을 리포트 머리에 먼저 적는다.
2. **재고.** 대상 GLB 전부를 센다. 파일 수와 재고 표의 줄 수가 같아야 한다.

   ```sh
   node .claude/skills/blender-pipeline/scripts/glb-inspect.mjs public/assets/<종류>/*.glb --json
   ```

3. **실측.** 돌릴 수 있는 장면이 있으면 [references/measurement.md](references/measurement.md)대로 조건을 고정하고 기준선을 잰다. 장면이 아직 없으면 2단계까지만 하고 "실측 없음, 자산 재고만"이라고 적는다.
4. **한계 가르기.** 화면 해상도를 절반으로 내려 다시 잰다. 프레임이 크게 오르면 GPU(화면 채우기, 셰이더, 겹쳐 그리기) 한계이고, 그대로면 CPU(드로 콜, 스크립트) 한계다. 처음 보일 때만 멈칫하면 셰이더 컴파일이나 텍스처 올리기다.
5. **후보 고르기.** 기준값을 넘는 것만 발견으로 올린다. 넘지 않은 것은 `## 점검했으나 변경 없음`에 적는다.
6. **발견 표.** 발견마다 근거 수치, 권고, 예상 효과를 적는다. 자산의 발견은 `자산 최적화` Task로 이어지고, 코드의 발견은 권고로 남는다.
7. **오래 돌리기.** 장면을 여러 번 드나든 뒤 그래픽 자원의 수가 처음과 같은지 본다. 늘면 해제 누락이다.

## 자산 최적화 절차

1. **사본.** 고치기 전의 GLB를 `_workspace/_run/<phase>/bak/<Task ID>/`에 복사한다. 원본 `.blend`는 건드리지 않는다.
2. **잃는 것이 없는 순서로.** 쓰지 않는 데이터 지우기(UV 세트, 정점 색, 셰이프 키, 빈 노드) → 텍스처 줄이기와 형식 바꾸기 → 재질 합치기와 한 장에 모으기 → 지오메트리 압축 → 거리별 단순 모델(LOD).
3. **수단.** 해당 `.blend`에서 다시 내보내거나(`blender-pipeline`을 로드한다), 자산 연동 규약이 채택한 도구를 쓴다. 프로젝트에 없는 도구는 새 의존성이므로 `ask`로 올린다. 압축은 규약이 정한 것만 쓴다. 런타임에 디코더가 없으면 열리지 않는다.
4. **하나 바꾸고 다시 센다.** 변경마다 변경 이력 표에 한 줄: 무엇을, 전과 후의 크기·삼각형·텍스처, 다시 잰 수치.
5. **이름이 그대로인지.** `glb-inspect.mjs --names`의 노드, 재질, 애니메이션 이름이 고치기 전과 같아야 한다. 최적화 도구는 기본값으로 노드를 합치고 이름을 지우는 경우가 있다. 코드가 이름으로 찾는 것이 깨진다.
6. **돌려보낼 것.** 실루엣이 달라지는 단순화, 텍스처 다시 그리기, 뼈 줄이기는 하지 않는다. 형태와 디자인이 바뀌는 일은 만든 담당의 몫이다. 권고로 적는다.

## 심각도

| 심각도 | 기준 |
| --- | --- |
| High | 예산의 상한을 넘는다. 또는 대상 기기에서 프레임 예산을 지키지 못하게 하는 원인이다 |
| Medium | 목표는 넘지만 상한 안이다 |
| Low | 예산 안이지만 적은 비용으로 줄일 수 있다 |

고치는 것은 High다. Medium 이하는 리포트의 `## 인박스 후보`에 한 줄씩 적는다.

## 리포트

뼈대는 `docs/harness/templates/report.md`다. 아래 절을 더한다.

```markdown
## 측정 조건
빌드 종류 / 화면 크기와 픽셀 비율 / 화면 주사율 / 브라우저와 Playwright 버전 / `probe-fps.cjs`의 판정 / 측정 횟수
기준값: <항목마다. 출처: 규약 또는 출발값>

## 재고
| 파일 | 크기(KB) | 삼각형 | 드로 콜 | 재질 | 텍스처(수, 최대 변) | 텍스처 메모리 추정(MB) | 뼈 | 클립 | 압축 |

## 기준선
| 시나리오 | 프레임 시간 p50 / p95 / 최장(ms) | 드로 콜 | 삼각형 | 자원 수(지오메트리, 텍스처) | 횟수 |

## 발견
| ID | 심각도 | 위치(자산, 또는 파일:줄) | 근거 수치 | 권고 | 예상 효과 | 상태 |

## 자산 변경 이력
| # | 변경 | 전 | 후 | 차이 | 다시 잰 값 |

## 코드 권고
| ID | 대상 | 권고 | 근거 |

## 점검했으나 변경 없음
## 인박스 후보
## 검증
```

- `## 발견`의 줄은 찾은 것이고, `## 검증`의 ❌는 내가 할 측정을 하지 못한 것이다. 섞지 않는다.
- 흉내 낸 조건(모바일 화면 크기, CPU 늦추기)으로 잰 값에는 "실기기 아님"이라고 적는다.

## 흔한 실수

| 실수 | 결과 |
| --- | --- |
| Playwright MCP의 창 없는 브라우저로 프레임을 판정 | 소프트웨어로 그려 한 자릿수가 나온다. 거짓 결함이다 |
| 개발 서버에서 잼 | 실제 빌드와 다른 수치 |
| 첫 실행을 기준선에 넣음 | 첫 회만 느려서 개선처럼 보인다 |
| 다른 워커가 도는 동안 잼 | 판정에 쓸 수 없다 |
| 주사율을 적지 않은 프레임 수 | 비교할 수 없다 |
| PNG를 JPEG로 바꾸면 그래픽 메모리가 준다고 적음 | 내려받는 크기만 준다 |
| 최적화 여러 개를 한 번에 적용 | 무엇이 효과였는지 모른다 |
| 고친 뒤 이름이 바뀐 것을 확인하지 않음 | 런타임이 노드와 클립을 찾지 못한다 |

## 완료 기준에 쓸 수 있는 검사

- 리포트 머리에 측정 조건과 기준값이 전부 있다.
- 재고 표의 줄 수가 대상 GLB 수와 같다.
- 기준값을 넘은 항목마다 발견 ID와 근거 수치가 있다.
- 고친 자산마다 변경 이력에 전과 후가 있고, `glb-inspect.mjs`에 예산을 넣어 코드 0이다.
- 고치기 전 사본이 `_workspace/_run/<phase>/bak/<Task ID>/`에 있고, 이름 목록이 전과 같다.
- 리포트의 수정한 파일 목록에 웹 코드(`src/`)가 없다(코드는 권고만 한다).
