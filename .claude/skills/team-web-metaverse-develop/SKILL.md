# team-web-metaverse-develop

웹 개발 팀은 그래픽 팀의 자산을 받아 사용자가 들어가 움직이는 월드와 그것을 감싸는 화면을 만든다. 3D 개발자와 UI 개발자는 약속 파일 하나로 만나고, 그 약속이 먼저 있어야 둘이 병렬로 간다. 팀장은 spec 첫 줄이 `[역할: metaverse-develop-leader · 리드]`인 워커이며 `team-lead`와 이 스킬을 로드한다.

## 에이전트 구성

| 에이전트 | 맡는 일 | 역할 스킬 | 모델 표의 작업 단위 |
| --- | --- | --- | --- |
| `metaverse-develop-leader` | 기준 문서 두 개(아키텍처, 자산 연동 규약) 쓰기 | `web-architecture` | 아키텍처 |
| `metaverse-3d-developer` | 3D 월드의 런타임: 불러오기, 캐릭터 조작, 애니메이션, 충돌, 카메라, 이펙트 재생, 동기화 | `web3d-runtime` | 3D 런타임 구현 |
| `metaverse-web-developer` | 화면과 기능: 페이지, 캔버스 위의 화면 요소, 상태 저장소, 서버 기능, 폼 | `web-feature` | UI·기능 구현 |

- 작업 단위는 모델 표에 있는 이름만 쓴다. 없으면 표에 줄을 먼저 넣는다.
- 팀장으로 뜬 `metaverse-develop-leader`는 기준 문서를 직접 쓰지 않는다. 같은 에이전트를 일반 Task로 따로 띄운다.

## 작업 흐름

| 순서 | 작업 | 담당 | 의존 | 산출물 파일 |
| --- | --- | --- | --- | --- |
| 01 | 아키텍처와 자산 연동 규약: 기준 문서를 쓰거나 이번 범위에 맞게 고친다 | `metaverse-develop-leader` | 브리프의 사용자 결정, 설계서 | `01_metaverse-develop-leader_architecture_v1.md` |
| 02 | 공용 약속: 3D와 UI가 함께 쓰는 타입, 저장소의 키와 행동, 이벤트 이름을 한 파일로 만든다 | 그 약속을 더 많이 쓰는 쪽(보통 `metaverse-3d-developer`) | 01 | `02_<에이전트>_contract_v1.md` |
| 03 | 3D 런타임 구현 | `metaverse-3d-developer` | 02. 쓰는 자산의 그래픽 Task | `03_metaverse-3d-developer_<기능>_v1.md` |
| 04 | UI·기능 구현 | `metaverse-web-developer` | 02 | `04_metaverse-web-developer_<기능>_v1.md` |
| 05 | 수정: 코드 리뷰와 QA의 High, 완료 기준 미달, 승인된 성능 권고 | 원래 구현한 에이전트 | 그 리포트 | 03, 04 리포트의 다음 버전 `_v<N+1>` |

- 순서 `NN`은 산출물 파일 이름의 `NN`이다. 도착 순서가 아니다.
- 03과 04는 02가 끝나면 함께 돈다. 상대 쪽을 기다리지 않도록 약속에 맞춘 가짜를 두고 만든다. 가짜는 제품에 남기지 않는다.
- **공용 파일은 Task 하나만 고친다.** 공용 약속 파일, `package.json`, 루트 설정 파일은 Task 하나의 편집 범위에만 넣고, 나머지 Task는 그 Task에 의존으로 건다. 다른 Task는 넣을 항목을 리포트에 적어 넘긴다.
- 코드가 아직 없으면 02 앞에 앱의 뼈대를 만드는 Task를 하나 둔다(담당 `metaverse-web-developer`, 루트 설정 파일을 편집 범위에 넣는다). 그 리포트에 검증 명령(타입 검사, 린트, 테스트, 빌드)과 돌린 결과를 적는다. `AGENTS.md`의 `명령` 절에 올리는 것은 `harness-engineer`의 일이다.
- 구현 Task의 완료 기준은 검증자가 그대로 돌릴 명령과 기대 출력으로 쓴다. 명령은 `AGENTS.md`의 `명령` 절에 있는 것만 쓴다. 구현자는 그 기준을 재현하는 테스트를 먼저 쓴다.
- 자산이 아직 없는 03은 자산 연동 규약에 맞춘 임시 자산으로 로직을 먼저 만들 수 있다. 그 경우 "진짜 자산으로 확인"을 뒤 Task로 계획에 넣는다.
- 새 의존성이 필요한 Task는 spec에 그 의존성과 사용자 결정의 출처를 적는다. 출처가 없으면 띄우지 않고 코디네이터에게 `ask`.
- 코드 리뷰와 실행 검증은 검증 팀이 한다(`team-qa`). 프레임과 자산의 실측은 `graphic-performance-verifier`가 한다. 이 팀은 고친다.

## 팀원 간 소통

- 기본은 팀장을 거친다. 팀원은 산출물 파일과 팀장의 `ask`/`reply`로 주고받는다.
- 아래 **직접 소통 짝 표**에 있는 짝만 서로 직접 메시지를 보낼 수 있다(`send --to dispatch:<상대 id>`). 팀장은 짝의 두 팀원을 띄운 뒤 서로의 Dispatch ID와 한도를 알려 준다.
- 받는 쪽은 알림(`You have N orchestration messages`)을 보면 `orca orchestration check`로 읽는다.
- 직접 주고받아 정한 내용은 보낸 쪽이 자기 리포트의 `## 직접 소통` 절에 적는다.

### 직접 소통 짝 표

| 짝 | 방향 | 용도 | 한도 |
| --- | --- | --- | --- |
| `metaverse-3d-developer` ↔ `metaverse-web-developer` | 양방향 | 공용 약속의 뜻 확인(키, 행동, 이벤트가 언제 무엇을 뜻하는가) | 기능 하나에 질문 3회, 넘으면 팀장에게 |

- **한도 칸은 비울 수 없다.** 짝을 더하면 한도를 함께 적는다.
- 약속을 바꾸는 일은 짝끼리 정하지 않는다. 바꿔야 하면 팀장에게 올리고, 팀장은 공용 약속 Task를 새로 띄운다.

## 작업 규모별 모드

| 모드 | 언제 | 투입 |
| --- | --- | --- |
| 풀 | 새 기능이 3D와 UI에 함께 걸친다. 구조나 규약의 결정이 필요하다 | 01부터 전부. Task가 3개 이상이므로 팀장을 띄운다 |
| 축소 | 기준 문서와 공용 약속이 있고 그 안에서 기능을 더한다 | 01을 건너뛴다. 약속에 더할 것이 없으면 02도 건너뛰고 03, 04 |
| 단일 | 한쪽만의 작은 변경, 결함 하나 수정 | 해당 에이전트 Task 하나. 코디네이터가 팀장 없이 직접 띄운다 |

## 산출물

- 리포트 경로: `_workspace/web-metaverse-develop/<phase>/NN_<에이전트>_<산출물>_v<N>.md`. 지시서는 `_workspace/web-metaverse-develop/<phase>/spec/`.
- 코드의 자리는 아키텍처 문서의 모듈 표가 정한다.
- 이미 넘긴 리포트는 고쳐 쓰지 않는다. 다시 쓰면 다음 버전 `_v<N+1>`을 만든다. `final`, `fix1`, `-2` 같은 접미사를 쓰지 않는다.
- 이 팀이 최신으로 유지하는 문서(`docs/live/web-metaverse-develop/`, 현재 상태만 담는다):

| 문서 | 소유 에이전트 | 갱신하는 때 |
| --- | --- | --- |
| `docs/live/web-metaverse-develop/architecture.md` | `metaverse-develop-leader` | 01. 구조, 모듈 경계, 3D와 UI 사이의 약속이 바뀌는 phase |
| `docs/live/web-metaverse-develop/asset-contract.md` | `metaverse-develop-leader` | 01. 자산의 형식, 이름, 예산이 바뀌는 phase. 그래픽 팀이 읽는다 |

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 기준 문서가 없는데 구현 Task를 받았다 | 01을 먼저 띄운다. 기술 결정이 브리프에 없으면 코디네이터에게 `ask` |
| 자산이 규약과 어긋난다고 팀원이 올렸다 | 코드로 맞추게 하지 않는다. 통합 보고의 `## 코디네이터 결정 필요`에 올려 그래픽 팀의 수정이나 규약의 변경 가운데 하나를 받는다 |
| 두 팀원이 약속을 다르게 읽었다 | 짝의 한도를 넘었으면 팀장이 정하지 않고, 약속을 분명히 하는 공용 약속 Task를 새로 띄운다 |
| 검증 명령이 없다 | 완료 기준을 지어내지 않는다. 뼈대 Task가 빠진 것이므로 먼저 띄운다 |
| 새 의존성이 필요하다고 팀원이 올렸다 | 코디네이터에게 `ask`. 사용자가 정한다 |
| 팀원 실패 | 원인을 새 spec에 적어 새로 띄워 1회 재시도. 그래도 실패하면 그 산출물 없이 통합 보고에 누락을 적는다 |

## 테스트 시나리오

- 정상: "캐릭터가 걸어 다니고 인사하면 효과가 터지며, 화면에 인사 버튼이 있다" → 풀 모드 → 01에서 인사 이벤트의 약속과 클립 이름을 문서에 넣음 → 02에서 `metaverse-3d-developer`가 약속 파일에 인사 행동과 이벤트를 더함 → 03(입력, 이동, 상태 기계, 큐 발행, 효과 재생)과 04(인사 버튼, 글자 입력 중 키 처리)가 함께 돈다 → 코디네이터가 검증 팀의 리뷰와 QA를 돌리고 High 하나 → 05에서 그 결함 ID의 재현 테스트부터 써서 고침 → 통합 보고.
- 기존 파일 활용: 기준 문서와 약속이 이미 있고 "설정 화면에 효과음 음량 추가" → 축소 모드 → 01과 02를 건너뛰고 04만, spec의 "먼저 읽을 것"에 아키텍처 문서의 상태 표와 이펙트 담당의 효과음 표를 넣는다.
- 오류: 03이 캐릭터 GLB의 클립 이름이 규약의 목록과 다르다고 올렸다 → 팀장이 코드로 맞추라고 답하지 않고 코디네이터에게 올림 → 그래픽 팀의 수정 Task가 끝난 뒤 03을 새로 띄운다.
