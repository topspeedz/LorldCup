## 1. 왜, 무엇을

사용자는 백로그의 남은 활성 항목을 한 phase로 끝내라고 하고 자리를 비웠다(브리프 요청 원문 2026-11-13). 범위는 BL-0025~BL-0032 여덟 개와 BL-0015·BL-0016의 남은 것이다. 정해진 기한은 없다.

이 문서는 다음에 답한다.

- 팀 단위의 굵은 흐름: 무엇이 함께 가고 무엇이 차례를 지켜야 하는가.
- 같은 파일(`web/screen-video.js`, `web/character.js`, `web/multiplayer.js`, `web/index.html`, `web/main.js`)에 여러 항목이 몰릴 때 서로 덮지 않게 가르는 선. 특히 거의 모든 화면 파일에 닿는 BL-0031의 차례.
- 새로 생긴 UX·UI 디자이너가 화면 작업 앞에서 명세를 내려보내는 흐름(UX 명세 → UI 명세 → 웹 적용)을 이 phase에 처음 넣는 자리.
- BL-0032의 방 구조(방 키 목록의 자리, 방장 넘기기, 혼자 시청, 영상 끊김 없음).
- 예상 시간, 임계 경로, 병렬 폭, 그리고 창구가 대행 채택한 결정(끝 절의 표).

## 2. 목표 · 비목표 · 실패 조건

**목표**

1. 열 개 항목의 수락 기준(정본은 `docs/backlog.md`의 각 행)을 끝 검증에서 통과시키는 흐름을 정한다. 통과하지 못하면 그 이유가 최종 보고와 인박스에 남는다(브리프 완료 기준).
2. 막힐 수 있는 항목(BL-0025: 로그인된 브라우저와 Blender가 필요)이 막혀도 나머지가 끝까지 간다.
3. 같은 시각에 두 흐름이 같은 파일을 고치지 않는다.
4. 화면 작업은 UX 명세 → UI 명세 → 웹 적용 순서로 내려간다.
5. 끝에 전체 시험(`npm test`) 1회를 돌린다(지난 phase에 건너뜀).

**비목표** (이번에 정하지 않는다)

- Task 단위 분해와 Task별 배정(계획 단계).
- push, PR, 배포, 정적 호스팅, TURN, signaling 이전, 유료 서비스, 새 계정.
- Next.js 전환.
- 공유 전 결정 묶음(J-7 글자 표지, J-10 트로피, 티켓 문구, 법률·Riot 재결정, "안 보일 때도 재생"의 J-2·J-3 재검토). 이번 phase의 변경이 이 묶음에 더할 줄만 적는다(5.6, 결정 14).

**실패 조건** (기술적으로 돌아가도 실패로 본다)

- 기존 기능의 회귀: TPS 이동, 점프, 방장 중심 WebRTC, 스크린 상시 재생과 자동 회복, Full Mode, 좌석, 티켓, 감정표현, 성능(경기장 FPS 60 이상, 텍스처 메모리 500 MiB 이하).
- 방장 넘기기나 혼자 시청으로 바뀔 때 보던 영상이 멈추거나 처음으로 돌아감(BL-0032 (4)(5)).

- 웹 런타임 라이브러리 추가, 유료 도구, 새 계정(브리프 금지).
- 막힌 항목 하나 때문에 다른 항목이 멈춤.

## 5. 구조

### 5.1 큰 모양: 세 줄의 로직과 한 줄의 화면, 그리고 막혀도 되는 한 줄

```
기동 ─┬─ W0  아키텍처·규약 갱신 ─┬─ 스크린 줄: 편성·U-H-10 → 소리·방 전환 무중단 ─ 중간 리뷰 ─┐
      │                        ├─ 방 줄: 순번 방 키·넘기기·혼자 시청·운영자 화면 ─ 중간 리뷰 ─┤
      │                        └─ 이펙트 줄: 연출 명세 → 런타임 이펙트·계란 명중 ────────────┤
      ├─ W0  아트 디렉션 보강 ┐                                                            │
      ├─ W0  UX 명세(2명) ────┴─ UI 명세 → 아트 대조 → UI 공용 틀 → 화면 적용 넷 + UX 동행 ┴─ 끝 리뷰 → 끝 QA → 성능 → 수정 → 재검 → 전체 시험
      ├─ W0  법무 앞 검토 ─────────────────────────────── (Mixamo 연결과 방 초대 적용이 읽는다)
      ├─ W0  Mixamo 내려받기 → 리타깃(Blender) → 클립 연결   ← 막히면 이 줄만 blocked
      └─ W0  먼 관중 화면 대조(BL-0015 (2))
```

- 로직은 화면 모양 없이 먼저 간다. 스크린·방·이펙트의 기능과 상태는 지금 화면 요소 안에서 만든다(문구는 임시). UI 명세가 나온 뒤 화면 적용 Task가 모양을 입힌다.
- 같은 파일을 로직과 화면 적용이 함께 고치는 곳(`screen-video.js`, `multiplayer.js`·`invite.js`)은 로직 줄 → 중간 리뷰 → 화면 적용 차례로 잇는다(5.2).

### 5.4 BL-0032 방 구조 (결정 8~12 채택)

**방 키.** 방 키는 정해진 순번(`01`, `02`, …, 상한 `maxRooms`)이고, 그 방의 지금 방장이 peer id `barclays-tps-room-<키>`를 쥔다. 키는 방에 붙어 있고 방장이 바뀌어도 그대로다. 비공개 무작위 코드 방은 없앤다(결정 11).

**자동 배치(수락 기준 (1)(2)(6)).** 입장 버튼을 누르면(결정 10) 앞 번호부터 차례로 잇는다.

| 받은 것 | 뜻 | 하는 일 |
| --- | --- | --- |
| 데이터 채널이 열리고 방장이 받아 줌 | 빈자리가 있는 방 | 그 방에 든다. 끝 |
| `full` | 16명이 찼다(지금의 정원 거절 그대로, `multiplayer.js:94-96,118`) | 다음 번호 |
| `peer-unavailable` | 그 번호에 방장이 없다 = 빈 번호 | 그 번호로 자리를 잡고 방장이 된다(새 방) |
| `unavailable-id`(자리를 잡다가) | 같은 순간 다른 사람이 먼저 잡았다 | 그 번호에 손님으로 다시 잇는다 |
| 시간 넘김 | 직접 연결 실패(TURN 없음) | 다음 번호 |

- 정원은 지금처럼 방장이 최종 판정한다. 마지막 사람이 나가면 peer id가 풀려 다음 사람에게 빈 번호가 된다(6).
- 빈 번호를 만날 때까지 가득 찬 방 수만큼 연결을 시도한다. 시간은 방 흐름의 첫 Task가 재고, 길면 몇 개씩 나란히 두드린다(R-13).

**운영자 화면(3).** `web/ops.html`(앱 화면에서 잇지 않는 별도 페이지)이 열려 있는 동안 1~`maxRooms`를 두드려 `info {count, capacity}`를 받아 방 키 목록과 방 개수를 보인다. 방장은 `hello {role: "ops"}`를 받으면 손님으로 세지 않고 `info`만 주고 닫는다. 사람에 대한 정보는 담지 않는다(법무 U-03).

**방장 넘기기(4).**

1. 방장은 들어온 순서의 손님 목록(`members`)을 상태 메시지와 함께 1초마다 다시 보낸다(`reliable: false`라 빠질 수 있다).
2. 방장이 탭을 닫으면(`pagehide`) `handoff {to}`를 보내고 Peer를 닫는다. id가 곧 풀린다.
3. 방장 연결이 끊기면 목록의 첫 사람이 새 방장이 된다. 남은 손님은 그 사람의 원래 peer id로 곧바로 다시 잇는다(목표 몇 초). 새 방장은 뒤에서 방 키의 peer id를 다시 잡는다. 앞 방장이 비정상으로 끊겨 id가 아직 안 풀렸으면 풀릴 때까지 재시도하고, 그동안 새로 오는 사람은 그 번호를 건너뛴다. PeerJS Cloud가 끊긴 id를 얼마나 쥐고 있는지는 모른다(R-2).
4. 새 방장이 정해진 시간 안에 응답하지 않으면 목록의 다음 사람으로 넘어간다.

**혼자 시청(5).** 다른 사람이 모두 나가도 남은 사람은 방장으로 남고 방 키를 쥔다. 운영자 화면과 자동 배치에 1/16 방으로 보인다. 안내 문구는 "혼자 시청 중"(UX 명세가 정함)이고 "방이 끊겼다"는 안내를 내지 않는다.

**영상 끊김 없음(4)(5).** 넘기기와 혼자 시청에서는 `room:left`를 내지 않는다. 방의 회차 시작 시각(`roundStart`)은 방에 붙어 다니고 바뀌지 않는다. 화면 모듈은 같은 회차의 `room:joined`를 다시 받아도 허용 오차 안이면 재생 위치를 옮기지 않는다. 사용자가 직접 방을 나가도 보던 회차를 그대로 이어 본다(F-2를 고친다). 재생 위치가 바뀌는 것은 처음 방에 들 때(그 방의 회차로 맞춤)와 재방이 끝나 방이 다음 회차로 넘어갈 때(결정 4)뿐이다.

**메시지.** 새 메시지(`members`, `handoff`, `hello`, `info`, 회차 넘김)는 모양을 검사한 뒤에만 쓴다(`architecture.md` `## 서버와의 통신`). `pose`·`validPose`·`window.arena.multiplayer`의 고정 속성은 그대로다.

**파일.** 분할선은 순번 키 찾기·자리 잡기(`web/room-keys.js`, 새 파일)와 넘기기·혼자 시청(`web/multiplayer.js`)이다. 둘은 a1이 적은 약속으로 나란히 가고, 잇기와 운영자 화면이 그 뒤다. 이 줄은 임계 경로와 15분 차이라 계획이 처음부터 나눈다(`phase-planning` 병렬 규칙 4).

### 5.5 스크린: 편성, U-H-10, 소리 (BL-0026, BL-0016, BL-0027)

한 파일(`web/screen-video.js`)이라 한 줄(sv)에서 Task 둘이 차례로 간다.

**sv-1 편성과 U-H-10.**

- 선택 상자를 없앤다(F-1). 화면 API의 `setSource`는 시험 손잡이로 남고, 편성이 다음 칸 경계에서 다시 정한다.
- 편성(결정 4): `screen.json`의 시간표 칸(`{from, to, source}`) 안이면 그 소스, 밖이면 재방. 생방송 칸에서 생방송이 오류·방송 없음·대기 상한에 걸리면 그 칸이 끝날 때까지 재방으로 넘어간다. 모두가 같은 설정을 읽으므로 같은 방 사람은 같은 소스를 본다.
- 재방이 끝나면 방장이 다음 회차를 알리고 방이 함께 넘어간다(혼자면 혼자 넘어간다). 지금의 "다른 회차의 방을 선택해 주세요"(`:149,168`)는 고를 사람이 없으므로 쓰지 않는다.
- U-H-10(결정 5): 먼저 원인을 가른다. 같은 재방 영상을 앱과, 앱 밖의 단독 임베드 페이지(`temp/` 아래 시험용, 제품 아님)에서 시간대를 나눠 5회씩 재생해 비교한다. 그 다음 반복 실패의 상태와 대기 상한을 설정값으로 둔다: 첫 실패부터 "다시 연결 중", 60초 안에 재생되지 않으면 기존 스크린 그림과 "연결이 원활하지 않아 계속 다시 시도합니다", 재시도 간격 상한 30초는 그대로.

**sv-2 소리와 방 전환 무중단.**

- 위치별 소리(결정 6): 스크린 중심과의 거리로 음량을 정한다(설정값). 앉은 상태와 Full Mode는 거리와 상관없이 설정 음량이다. 유튜브 플레이어 `setVolume`만 쓴다(소리를 가공하지 않는다).
- 경기장 밖(결정 7): 지금 규칙 그대로(보일 때만 재생). 경기장 경계 값(`:277`의 숫자)을 설정으로 옮긴다.
- 방 전환 무중단(5.4): `room:left`와 같은 회차의 `room:joined`에서 위치를 옮기지 않는다. 방 밖의 10분 되감기(`:296`)는 재생을 한 번 시작한 뒤에는 하지 않는다.

### 5.6 이펙트: 감정표현 4종과 계란 (BL-0028, BL-0029)

- **만드는 곳(결정 13).** Blender 자산을 만들지 않고 웹 런타임에서 코드로 그린 입자와 그림(canvas 텍스처)으로 만든다. 지난 phase의 하늘 쇼와 선수 동작이 같은 방식이었다. `graphic-effect-vfx-designer`는 연출 명세와 큐 표(색은 아트 디렉션 보강의 이펙트 톤, 순간은 클립의 이름 붙은 프레임)를 쓰고, `metaverse-3d-developer`가 `character.js`에 재생을 만든다.
- **큐.** 지금 박혀 있는 프레임(F-11)과 클립 파일 경로를 `characters.json`으로 옮긴다. 이펙트는 "손이 마주치는 프레임"처럼 클립 표의 이름 붙은 순간에 붙는다. BL-0025가 클립을 바꾸면 b25i가 그 값만 바꾼다.
- **원격(BL-0028 (2), BL-0029 (2)).** 지금의 감정표현 동기화(`peer:state`의 `emoteSeq`)로 원격 아바타에서도 같은 코드가 재생한다. 새 메시지는 없다. 계란의 비행은 각자 던진 사람의 아바타 위치에서 계산한다.
- **계란(BL-0029).** 놓는 프레임에 던진 사람의 손에서 출발해, 던진 사람 쪽을 가장 바로 보는 스크린 면(`window.arena.screen.faces`, F-12)의 한 점으로 정해진 비행 시간(설정값) 안에 날아가 맞는다. 맞으면 껍데기 조각과 노른자 자국이 면 위에 생기고 정해진 시간(결정 14) 안에 사라진다. 플레이어 DOM은 건드리지 않으므로 영상은 끊기지 않는다(3). 스크린 흐름(sv)은 `faces`의 모양을 바꾸지 않는다(a1이 약속으로 적는다).
- **예산.** 이펙트 텍스처는 합 2 MiB 이하(출발값, 텍스처 메모리 여유 8.5 MiB, F-13), 동시에 보이는 입자 수 상한은 설정값. 이 흐름의 완료 검사에 `tests/qa-p.spec.mjs` 메모리 단언과 FPS 시험을 넣는다. FPS 60 이상(BL-0028 (3))은 끝의 성능 점검이 판정한다.
- **함께 고칠 것(결정 16).** 원격 아바타를 다시 만들 때 마지막 감정표현이 다시 재생되는 결함(인박스 T41 R-1, `character.js:76`·`:114`)은 이펙트가 붙으면 계란이 다시 날아가 BL-0029 판정을 흐린다.

### 5.10 약속의 출발값 (a1이 확정한다)

- **이벤트:** 방 상태(예: `room:state {key, count, host, phase}`, `phase`는 연결 중·방 안·넘기는 중·혼자), 회차 넘김(예: `room:round {roundStart}`). `room:left`는 사용자가 나갈 때만 낸다. 기존 `room:joined {code, host, roundStart}`의 `code` 자리에 방 키가 든다.
- **화면 API:** `window.arena.screen.faces`는 읽기 전용 고정 약속(이펙트와 좌석이 읽음). `setSource`는 시험 손잡이. 편성 상태를 시험이 읽을 손잡이를 더한다.
- **설정 키:** `screen.json`의 편성·대기 상한·거리 음량·경기장 경계, `network.json`의 방 키 접두어·`maxRooms`·연결 시간 넘김·넘기기 대기·운영자 화면 갱신 간격, `characters.json`의 클립 경로·큐 프레임·이펙트 값.
- **자산:** `fan-anim-v2.glb`는 `fan-anim.glb`와 같은 뼈·클립 이름·예산. 이펙트는 자산이 아니라 런타임(텍스처 합 2 MiB 출발값).
- **고정 ID:** 5.2의 목록과 `index.html` 예외.

## 9. 비용과 의존성

- 비용 0원. 새 계정 없음. Mixamo는 사용자의 기존 Adobe 계정으로 사용자 브라우저에서만 받는다.
- 새 웹 런타임 라이브러리 없음. 이펙트는 Three.js r170만으로 그린다. 방은 지금의 PeerJS(`web/vendor/peerjs.min.js`)만 쓴다.
- 시험 의존성: 여러 사람 방 시험은 `tests/qa-x.spec.mjs`처럼 git 밖의 로컬 PeerServer를 다시 쓴다(F-16). 저장소에 새 패키지를 넣지 않는다.
- Higgsfield, `generate_3d`, 유료 이미지 생성, CDN 글꼴은 쓰지 않는다. 디자인 스킬은 이 조건 안에서만 쓴다.
- 법무 검토는 `legal-reviewer`만 띄운다. Riot 표지와 게임 화면을 바꾸는 변경이 없어 `riot-policy-reviewer`는 필요 없다(공유 전 묶음은 그대로).
