# 방 서버 구조 설계 (BL-0022)

- 읽는 시점: 공개 방 찾기·랜덤 입장·자동 배치를 구현하기로 정할 때, 방 id 목록을 둘 곳이나 호스팅·TURN을 정할 때
- 범위: 방 생성, 초대 접속, 회차별 공개 방 찾기, 랜덤 입장과 배치의 흐름. 그 흐름에서 방 id 목록(서버 역할), signaling, TURN이 각각 맡는 일
- 상태: phase 2026-11-13-ux-motion-rooms가 후보 E(정해진 순번의 방 키, `### 채택한 후보 E`)로 구현한다. 방 구조의 정본은 `docs/live/web-metaverse-develop/architecture.md`의 `## 방 구조`다. 이 문서에서 그와 다른 곳(16자리 방 코드, 회차별 방과 회차 고르기, 공개·비공개, 방장이 나가면 방이 끝남, 목록이 받는 요청, 후보 A~D의 "다음 단계")은 채택하지 않은 설계다. 호스팅, TURN, signaling 이전은 여전히 정해지지 않았다
- 소유 에이전트: metaverse-develop-leader
- phase: 2026-11-12-requirements-build (T12)

지금 앱의 연결 약속(메시지 모양, 이벤트, 설정 파일)은 `docs/live/web-metaverse-develop/architecture.md`의 `## 서버와의 통신`이 정본이다. 이 문서는 그 약속을 바꾸지 않고 그 위에 얹을 구조를 적는다. 공급자, 요금제, DB는 정하지 않았다. `## 결정 필요`에 후보로 남긴다.

## 한눈에

앱은 서버 코드가 없는 정적 Three.js 앱이다. 브라우저끼리 WebRTC 데이터 채널로 직접 잇고, 방을 만든 사람의 브라우저가 방장이 되어 위치와 상태를 중계한다. 영상은 주고받지 않는다. 각자 자기 유튜브 플레이어로 본다.

```
 방장 브라우저 ──① peer id 등록──▶ PeerJS Cloud ◀──② 방장 id로 연결 요청── 참가자 브라우저
      │                           (signaling)                                │
      │                                                                      │
      └────────③ WebRTC 데이터 채널: pose · world · state · room ────────────┘
      │           주소 찾기는 STUN. 직접 이어지지 않으면 TURN(후보, 지금 없음)
      │
      └─(다음 단계) 방 등록·인원 알림──▶ 방 id 목록 ◀──회차별 공개 방 찾기·배치── 들어갈 사람의 브라우저
                                      (서버 역할)
```

네 요소는 서로 다른 일을 한다. 하나가 다른 것의 일을 대신하지 않는다.

| 요소 | 하는 일 | 하지 않는 일 | 지금 | 누가 운영하나 |
| --- | --- | --- | --- | --- |
| 방장 브라우저 | 방을 만든다. 정원을 지킨다. 위치·상태를 중계한다. 방의 회차를 알려 준다 | 영상 전달, 다른 방을 아는 일 | 있다 | 방을 만든 접속자 |
| 방 id 목록 (서버 역할) | 만들어진 공개 방의 id·회차·정원·빈자리·종료 상태를 갖고, 들어갈 사람에게 방을 골라 준다 | 연결 중개, 위치·상태·영상 전달, 정원의 최종 판정 | 없다(다음 단계) | 운영자 |
| signaling | 두 브라우저가 WebRTC 연결을 맺기 전에 연결 정보(offer, answer, ICE 후보)를 서로에게 건넨다. peer id를 맡아 둔다 | 방 목록, 빈자리, 회차, 연결된 뒤의 데이터 전달 | PeerJS Cloud | PeerJS(공개 무료 서비스) |
| TURN | 두 브라우저가 직접 이어지지 않을 때 데이터를 대신 중계한다 | 연결 중개, 방 목록 | 없다(후보) | 정하지 않음 |

## 흐름

"이번 phase"는 T13(화면)과 T27(멀티)이 만드는 것이고, "다음 단계"는 방 id 목록이 생긴 뒤의 것이다.

### 회차

- 회차 시작 시각 `roundStart` = 지금 시각을 회차 간격(10분)으로 내림한 값이다. epoch 밀리초로 다룬다. 매시 00·10·20·30·40·50분이 회차의 시작이고, 시간대가 달라도 같은 회차를 가리킨다.
- 방은 만들어질 때 회차 하나를 갖고 끝날 때까지 바꾸지 않는다.
- 방 안의 재생 위치 = 지금 시각 − 그 방의 `roundStart`. 이 값을 유튜브 주소의 시간 정보(`start`)에 넣어 강제로 맞춘다. 중간에 들어온 사람도 같은 식을 쓴다. 계산은 각자 한다(`roundPosition`, 아키텍처 문서의 화면 API).
- 방의 영상이 끝나면 기존 스크린 그림과 안내를 보인다.
- 진행 중인 회차 = `roundStart` ≤ 지금 < `roundStart` + 영상 길이. 영상이 회차 간격보다 길면 여러 회차가 동시에 진행 중이다.
- 생방송은 맞추지 않고 각자 본다. 회차가 재생에 쓰이지 않는다.
- 회차 간격과 기본 회차(방금 시작한 회차)는 설정값이다(`web/config/screen.json`, `web/config/network.json`).

### 방 만들기

| 단계 | 일어나는 일 | 언제 |
| --- | --- | --- |
| 1 | 만드는 사람이 회차를 고른다. 기본값은 방금 시작한 회차 | 이번 phase |
| 2 | 브라우저가 방 코드(16자리 16진수)를 만들고 peer id `barclays-tps-<방 코드>`로 signaling에 등록한다. 등록되면 그 사람이 방장이다 | 지금 있다 |
| 3 | 만드는 사람이 공개 방으로 할지 고른다. 공개 방이면 방장 브라우저가 방 id 목록에 방을 올린다(방 코드, `roundStart`, 정원, 지금 인원) | 다음 단계 |
| 4 | 방장 브라우저가 사람이 들고 날 때와 일정 간격마다 인원을 목록에 알린다 | 다음 단계 |

공개하지 않은 방은 목록에 오르지 않는다. 방 코드를 아는 사람만 들어온다.

### 초대 접속

| 단계 | 일어나는 일 | 언제 |
| --- | --- | --- |
| 1 | 방 안의 사람이 방 코드가 든 초대 URL을 복사해 건넨다 | 이번 phase |
| 2 | 받은 사람이 URL을 열면 브라우저가 signaling에 임의의 peer id로 등록하고, 방장 id로 연결을 요청한다 | 지금 있다(코드 입력), URL은 이번 phase |
| 3 | 데이터 채널이 열리면 방장이 `room {roundStart}`를 보낸다. 들어온 사람은 그 방의 회차를 따른다 | 이번 phase |
| 4 | 방이 가득 찼으면(17번째) 방장이 "방이 가득 찼습니다(16명)"를 알리고 연결을 닫는다 | 이번 phase |

초대 접속은 방 id 목록을 거치지 않는다. 목록이 없거나 멈춰도 방 만들기와 초대 접속은 그대로 된다.

### 회차별 공개 방 찾기 (다음 단계)

1. 들어갈 사람이 진행 중인 회차 가운데 하나를 고른다. 기본값은 방금 시작한 회차다.
2. 브라우저가 방 id 목록에 그 회차의 공개 방을 묻는다.
3. 목록이 빈자리가 있고 끝나지 않은 방을 돌려준다(방 코드, 인원, 정원).
4. 화면이 회차마다 방의 수와 빈자리를 보여 준다. 사람이 방을 골라 들어가면 그 뒤는 초대 접속의 2~4단계와 같다.

진행 중인 회차가 많을수록 사람이 회차마다 흩어진다. 찾기 화면이 회차별 인원을 보여 주어 사람이 있는 회차로 모이게 한다.

### 랜덤 입장과 자동 배치 (다음 단계)

1. 들어갈 사람이 회차를 고르고(기본값: 방금 시작한 회차) "아무 방이나"를 누른다.
2. 브라우저가 방 id 목록에 그 회차의 배치를 요청한다. 목록이 빈자리가 있는 방 가운데 몇 개를 순서를 매겨 돌려준다. 고르는 기준은 `## 결정 필요`에 있다.
3. 브라우저가 첫 방부터 연결을 시도한다. 아래 세 경우에는 다음 방으로 넘어간다.
   - 방장이 이미 나갔다(signaling이 `peer-unavailable`을 준다).
   - 그 사이에 방이 가득 찼다(방장이 가득 참을 알리고 닫는다).
   - 연결 시간이 넘었다.
4. 받은 방이 없거나 모두 실패하면 그 회차의 새 공개 방을 만들고 방장이 된다(방 만들기 2~4단계).

### 방이 끝날 때

- 방장이 나가면 방이 끝난다. 남은 사람에게 안내한다. 방장 넘기기와 다시 잇기는 없다(지금 구조 그대로).
- 다음 단계: 방장 브라우저가 나갈 때 목록에 종료를 알린다. 탭을 그냥 닫거나 망이 끊기면 알리지 못하므로, 목록은 인원 알림이 일정 시간 오지 않은 방을 끝난 방으로 본다.
- 영상이 끝난 회차의 방은 방장이 남아 있어도 찾기와 배치에서 뺀다.

## 서버 역할

서버가 하는 일은 하나다. 만들어진 공개 방의 id 목록을 갖고, 그것으로 사람을 방에 배치한다. 연결을 중개하지 않고, 위치·상태·영상을 전달하지 않는다.

signaling만으로는 이 일을 할 수 없다. signaling은 peer id만 알고, 그 id가 어느 회차의 방인지, 몇 명이 있는지, 공개 방인지를 모른다.

### 목록이 갖는 것

| 칸 | 뜻 | 누가 쓰나 |
| --- | --- | --- |
| 방 코드 | 16자리 16진수. 방장의 peer id는 여기서 나온다 | 방장 브라우저(올릴 때) |
| `roundStart` | 그 방의 회차 시작 시각(epoch 밀리초). 회차 간격의 배수 | 방장 브라우저(올릴 때) |
| 정원 | 16 | 방장 브라우저(올릴 때) |
| 인원 | 방장 포함 지금 인원. 빈자리 = 정원 − 인원 | 방장 브라우저(알릴 때마다) |
| 마지막 알림 시각 | 목록이 받은 시각. 종료 판정에 쓴다 | 목록 |
| 상태 | 열림, 가득 참, 끝남, 숨김 | 목록(인원과 알림 시각에서 계산), 운영자(숨김) |

사람에 대한 정보(닉네임, 팀, 캐릭터, 위치)는 목록에 넣지 않는다.

### 목록이 받는 요청

모양의 출발값이다. 주소, 인증, 응답의 정확한 모양은 구현 phase의 아키텍처 Task가 정한다.

| 요청 | 누가 | 담는 것 | 결과 |
| --- | --- | --- | --- |
| 방 올리기 | 방장 브라우저 | 방 코드, `roundStart`, 정원, 인원 | 목록에 방이 생긴다 |
| 인원 알리기 | 방장 브라우저 | 방 코드, 인원 | 인원과 마지막 알림 시각이 바뀐다 |
| 방 끝내기 | 방장 브라우저 | 방 코드 | 상태가 끝남이 된다 |
| 회차의 방 찾기 | 들어갈 사람의 브라우저 | `roundStart` | 그 회차의 열린 방 목록(방 코드, 인원, 정원) |
| 배치 받기 | 들어갈 사람의 브라우저 | `roundStart` | 시도할 방 몇 개(순서 있음). 없으면 빈 목록 |
| 방 숨기기·지우기 | 운영자 | 방 코드 | 찾기와 배치에서 빠진다 |

### 목록과 방장 사이에서 누가 정하나

- 정원의 최종 판정은 방장이 한다. 목록의 인원은 알림 간격만큼 늦은 값이다. 두 사람이 마지막 한 자리에 함께 배치되면 방장이 한 사람을 가득 참으로 돌려보내고, 그 사람은 다음 방으로 넘어간다.
- 방이 살아 있는지의 최종 판정은 signaling과 방장이 한다. 목록에 남은 끝난 방은 연결 시도에서 `peer-unavailable`로 드러난다.
- 목록은 힌트다. 목록이 틀려도 정원이 넘치거나 다른 회차의 사람이 섞이지 않는다. 방의 회차는 방장이 보내는 `room {roundStart}`가 정한다.

### 알릴 위험

| 위험 | 내용 | 줄이는 방법(다음 단계) |
| --- | --- | --- |
| 쓰는 요청을 믿을 수 없다 | 정적 앱에는 비밀값을 둘 수 없어, 누구든 방 올리기 요청을 흉내 낼 수 있다 | 모양 검사(방 코드 16자리 16진수, `roundStart`가 회차 간격의 배수이고 진행 중인 회차, 인원 1~정원), 요청 빈도 제한, 알림이 끊긴 방 자동 종료, 운영자의 숨기기 |
| 가짜 방 | 없는 방은 연결 시도에서 걸러진다. 실제로 열린 악의의 방은 걸러지지 않는다 | 운영자의 숨기기. 받은 메시지는 모양을 검사한 뒤에만 쓰고 닉네임은 글자로만 넣는다(아키텍처 문서) |
| 기기 시계 | 시계가 틀린 사람은 회차와 재생 위치가 어긋난다 | 목록의 응답에 서버 시각을 실어 차이를 고친다(후보) |
| 접속 기록 | 목록을 두는 서비스에는 요청한 쪽의 IP 주소가 남는다 | 구현을 정할 때 `legal-review` 팀의 개인정보 검토를 받는다 |
| 목록이 멈춘다 | 공개 방 찾기와 배치만 멈춘다. 방 만들기, 초대 접속, 이미 이어진 방은 그대로다 | 찾기 화면이 "방을 직접 만들거나 초대 링크로 들어가세요"를 안내한다 |

### 목록을 둘 곳의 후보

정하지 않았다. 종류별로 얻는 것과 잃는 것만 적는다. 요금과 한도는 정할 때 공식 자료로 확인한다.

| 후보 | 모양 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| A. 서버 함수 + 작은 저장소 | 요청 여섯 개를 받는 함수와, 만료 시간이 있는 키-값 저장소. Vercel(필요하면 유료)이 이 후보다. 정적 파일 호스팅과 한곳에 둘 수 있다 | 빈자리가 실시간에 가깝다. 모양 검사와 빈도 제한을 서버에서 한다. 서버 시각을 줄 수 있다 | 외부 서비스와 계정이 하나 생긴다. 무료 구간을 넘으면 비용이 든다. 저장소 종류를 또 골라야 한다 |
| B. 브라우저가 직접 쓰는 관리형 실시간 DB | 함수 없이 DB의 접근 규칙만으로 방장이 쓰고 모두가 읽는다 | 서버 코드가 없다. 목록의 변화를 밀어 받을 수 있다 | 웹 런타임 라이브러리가 하나 늘 수 있다(지금 금지된 일이라 사용자 결정). 검사를 DB 규칙으로만 한다 |
| C. PeerJS 위의 로비 peer | 운영자가 정해진 peer id로 로비 페이지를 열어 둔다. 방장과 들어갈 사람이 그 peer에 데이터 채널로 묻고 알린다 | 새 서비스와 비용이 없다. PeerJS만 쓴다 | 운영자의 브라우저가 켜져 있어야 한다. 로비가 꺼지면 찾기가 멈춘다. 로비도 TURN이 없어 일부 망에서 닿지 않는다. 한 브라우저가 받는 연결 수에 묶인다 |
| D. 운영자가 손으로 고치는 정적 목록 | 방장이 방 코드를 운영자에게 알리고, 운영자가 정적 파일(JSON)에 적어 올린다 | 서버가 없다. 호스팅만 있으면 된다 | 빈자리와 종료를 모른다(들어가 봐야 안다). 방이 생길 때마다 사람이 손을 댄다 |

### 채택한 후보 E

phase 2026-11-13-ux-motion-rooms가 고른 것이다(설계서 `docs/superpowers/specs/2026-11-13-ux-motion-rooms-design.md` 5.4, 결정 8). 방 키를 정해진 순번(`01` ~ `maxRooms`)으로 두고, 그 방의 방장이 peer id `barclays-tps-room-<방 키>`를 쥔다. 목록을 두는 곳이 따로 없다. 들어갈 사람은 앞 번호부터 두드려 빈자리가 있는 방에 들거나 빈 번호의 방장이 되고, 운영자 화면(`web/ops.html`)은 같은 번호를 두드려 방 키 목록과 방 개수를 본다. 새 서비스, 계정, 비용, 런타임 라이브러리가 없다. 잃는 것은 가득 찬 방 수만큼 드는 찾기 시간, 방 수의 상한, 비공개 방, 운영자 화면이 열려 있을 때만 보이는 목록이다. 약속(자동 배치 표, 방 메시지, 방장 넘기기, 혼자 시청)은 `docs/live/web-metaverse-develop/architecture.md`의 `## 방 구조`가 정본이다.

## signaling

signaling은 PeerJS Cloud다(지금 방식 그대로). 두 브라우저가 WebRTC 연결을 맺는 데 필요한 정보만 건네고, 연결이 맺어진 뒤의 데이터는 지나가지 않는다.

| 항목 | 내용 | 근거 |
| --- | --- | --- |
| 서비스 | PeerJS Cloud 기본 서버(`0.peerjs.com:443`). 앱은 주소를 따로 적지 않고 PeerJS 1.5.5의 기본값을 쓴다 | `web/multiplayer.js:52`, V02 리포트 |
| 방장의 id | `barclays-tps-<방 코드>`. 방 코드는 방장 브라우저가 만든 16자리 16진수 | `web/multiplayer.js:50-51` |
| 참가자의 id | signaling이 주는 임의의 id | `web/multiplayer.js:52` |
| 건네는 것 | offer, answer, ICE 후보. 접속을 지키는 신호(5초마다) | V02 리포트 |
| 지나가지 않는 것 | `pose`, `world`, `state`, `room`. 영상 | `web/multiplayer.js:60,80-82` |
| 주소 찾기 | Google STUN(`stun.l.google.com:19302`). 브라우저가 자기의 바깥 주소를 알아내는 데만 쓴다. 데이터를 중계하지 않는다 | `web/multiplayer.js:52` |
| 방장의 접속이 끊기면 | 지금은 방을 끝낸다 | `web/multiplayer.js:71` |

signaling에 생기는 일과 화면의 안내(지금 코드에 있다):

| 일 | 뜻 | 안내 |
| --- | --- | --- |
| `peer-unavailable` | 그 방 코드의 방장이 접속해 있지 않다 | 방을 찾을 수 없습니다 |
| `unavailable-id` | 같은 방 코드가 이미 쓰이고 있다 | 방 코드가 사용 중입니다 |
| `network`, 25초 넘김 | signaling에 닿지 못했다 | 연결 중개 서비스에 접속할 수 없습니다 |
| `webrtc`, 20초 넘김 | signaling은 됐으나 두 브라우저가 직접 이어지지 않았다. TURN이 있어야 풀리는 경우다 | 브라우저 사이의 직접 연결에 실패했습니다 |

공개 방 배치(다음 단계)는 `peer-unavailable`과 시간 넘김을 "다음 방으로 넘어가라"는 신호로 쓴다.

signaling이 하지 않는 것: 방 목록, 빈자리, 회차, 공개 여부를 모른다. 방 코드가 추측하기 어려운 값이라, 공개하지 않은 방은 코드를 받은 사람만 닿는다.

기대는 것과 한계(V02 리포트, 2026-11-12 공식 자료):

- 무료다. 동시 peer 수, 메시지 수, 가용성에 대한 공식 수치와 보장을 찾지 못했다.
- PeerJS는 사용량이 많은 앱에 자기 서버를 권한다.
- signaling이 멈추면 새 방 만들기와 새 접속이 되지 않는다. 방장의 접속이 끊기면 지금 코드는 방을 끝낸다.

바꿀 때의 후보(지금은 고르지 않는다): 자기 PeerServer를 띄운다. 항상 켜져 있고 WebSocket을 받는 서버가 필요하다. 앱에서는 `Peer`를 만들 때의 주소만 바뀌고 방 코드, 메시지, 방 id 목록은 그대로다.

## TURN

TURN은 후보다. 지금은 없고, 이번 phase에 쓰지 않는다.

| 항목 | 내용 |
| --- | --- |
| 하는 일 | 두 브라우저가 직접 이어지지 않을 때(회사·학교 망, 일부 모바일 망의 엄격한 NAT와 방화벽) 데이터를 대신 중계한다 |
| signaling과 다른 점 | signaling은 연결을 맺기 전의 정보만 건넨다. TURN은 맺어진 뒤의 데이터 자체를 나른다. 그래서 TURN은 나른 양만큼 비용이 든다 |
| STUN과 다른 점 | STUN은 주소만 알려 주고 데이터를 나르지 않는다 |
| 방 id 목록과 다른 점 | 방을 모른다. 배치와 무관하다 |
| 지금 | 없다. 직접 이어지지 않는 사람은 방에 들어오지 못하고 "브라우저 사이의 직접 연결에 실패했습니다" 안내를 본다. 직접 이어지는 사람에게는 영향이 없다 |
| 나르게 될 것 | `pose`, `world`, `state`, `room`뿐이다. 영상은 각자 유튜브에서 받으므로 TURN을 지나지 않는다 |

TURN을 쓰기로 하면 따라오는 것:

1. TURN 공급자와 계정(사용자 결정, 비용).
2. 인증 정보를 내주는 서버 기능. 오래 쓰는 키를 브라우저에 두면 안 되므로, 짧게 쓰고 버리는 인증 정보를 서버가 만들어 준다. 방 id 목록과는 다른 역할이고, 후보 A를 고르면 같은 곳에 둘 수 있다. 후보 C·D만으로는 이 기능을 둘 곳이 없다.
3. 앱 쪽은 `Peer`를 만들 때의 `iceServers`에 TURN을 더하는 일뿐이다(`web/multiplayer.js`). 메시지와 방 구조는 그대로다.
4. 방장 중심이라 중계가 필요한 연결만 TURN을 지난다. 방장의 망이 엄격하면 그 방의 모든 연결이 TURN을 지난다.

비용의 크기(V02 리포트의 계산이고 실측이 아니다): 상태 메시지만, 20명, 한 달 60시간, 모든 연결이 중계된다고 가정하면 122.14 GB다. 비교용으로 본 Cloudflare Realtime TURN은 한 달 1,000 GB까지 무료이고 그 뒤 1 GB에 0.05달러다. 공급자를 고른 것이 아니다.

쓸지 정하는 근거가 아직 없다. 인터넷망에서 직접 연결이 얼마나 실패하는지 잰 적이 없다(V01은 로컬망에서만 쟀다).

## 정적 파일 호스팅

이번 phase에는 배포가 없다. 여러 사람이 쓰려면 `web/`을 올릴 호스팅이 필요하고, 정해지지 않았다.

- Vercel(필요하면 유료)이 후보다. 방 id 목록의 후보 A와 한곳에 둘 수 있다.
- Cloudflare 임시 터널은 전제로 삼지 않는다. 개발·시험용이고 가용성 보장이 없으며 다시 띄울 때마다 주소가 바뀐다(V02 리포트).
- 고를 때 볼 것: HTTPS(WebRTC, 포인터 잠금, 클립보드 복사, 유튜브 임베드가 기댄다), 파일 하나의 크기 상한과 전송량 한도. 지금 경기장 GLB가 120.6 MB, 라이트맵 PNG가 합쳐 약 151 MB다(설계서 F-9, F-10).
- 초대 URL은 호스팅 주소에 방 코드를 붙인 것이다. 주소가 바뀌면 이미 건넨 초대 링크가 죽는다.

## 유효한 결정

| 결정 | 맥락 | 고르지 않은 것과 이유 | 잃는 것 |
| --- | --- | --- | --- |
| signaling은 PeerJS Cloud | 사용자 결정. 지금 앱의 방식 | 자기 PeerServer: 항상 켜진 서버가 필요하다. Cloudflare 임시 터널: 여러 사람이 쓰는 서비스의 전제가 아니다 | 수용량과 가용성을 보장받지 못한다 |
| 방은 접속자가 만들고 만든 사람이 방장 | 사용자 결정. 지금 앱의 방식 | 서버가 방을 만들고 중계: 서버와 비용이 생긴다 | 방장이 나가면 방이 끝난다. 방장의 기기와 망이 방의 품질을 정한다 |
| 서버 역할은 방 id 목록과 배치뿐 | 사용자 결정("만들어진 방 id만 관리해서 배치에 도움되게끔만") | 서버가 위치·상태를 중계: 트래픽과 비용이 서버로 간다 | 서버가 방 안을 모른다. 정원과 생사를 방장과 signaling이 정하므로 목록은 늦거나 틀릴 수 있다 |

| 방 하나는 한 회차에 속하고 `roundStart`로 구분한다 | 사용자 확인. 재생 위치를 각자 계산한다 | 방장이 재생 위치를 보내 맞추기: 메시지와 방장 의존이 는다 | 진행 중인 회차 수만큼 사람이 나뉜다. 기기 시계에 기댄다 |
| TURN은 쓰지 않는다 | 이번 phase는 비용 없이 간다(결정 24) | 유료 TURN: 비용, 그리고 인증 정보를 내줄 서버가 필요하다 | 직접 이어지지 않는 망의 사람은 들어오지 못한다 |
| 이번 phase는 설계 문서만 | 결정 27. Vercel을 쓰지 않는다 | 지금 구현: 공급자와 비용이 정해지지 않았다 | 공개 방 찾기와 랜덤 입장이 없다. 초대 링크로만 만난다 |
